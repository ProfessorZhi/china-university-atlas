
- JS（单一常量，已存在）：`src/app.js:7` `const FONT_STACK='<同一个字符串>'`。`city-layer.js` 与其余层可以直接引用它 —— 依据是 `scripts/build.py:184` 把所有 JS 拼进同一个 `<script>`，顶层 `const` 在同一脚本内可见（当前 `city-layer.js:284` 已在这么用）。**任何时候不要在 JS 里再写字面字体族**。
- 建议补两处（当前仍是字面量）：`app.js:89` 的导出标题改用 `FONT_STACK`；并在 `makeSVG()` 里给导出 SVG 的根节点补 `svg.setAttribute('font-family',FONT_STACK)`，否则"另存为 SVG"在离线环境里没有 CSS 可继承，21px 标题与 10px 页脚（含三个 `·`）会落到 UA 默认字体族。

### 排序逻辑评估（per-glyph fallback，不是整段选一款字体）

CSS 字体回退是**逐字符**的：浏览器按列表顺序逐款查字体，谁先包含该字符就用谁；某一款虽然存在但不含该字符，也会被跳过。因此：

- **对汉字，列表顺序无关紧要。** `-apple-system`（SF）与 `"Segoe UI"` 都不含汉字，查不到就继续往后走，最终落到 `"PingFang SC"`（macOS）/ `"Microsoft YaHei"`（Windows）/ `"Noto Sans CJK SC"`（Linux）。实测佐证（Windows，Chrome 152）：完整的候选栈与只写 `"Microsoft YaHei"` 渲染出的汉字 ink box **完全一致**（`getBBox().width=46.203`, `height=15`），说明汉字确实由 YaHei 画出，而不是被前面的拉丁字体截走。
- **顺序只在"多款字体都能画"的字符上有意义**：拉丁字母、数字、ASCII 标点、`·`(U+00B7)、空格、`＋`(U+FF0B) 等。这些字符取列表**最前面那款存在且含该字形**的字体。实测（Windows，11.3px）：

  | 字符 | `"Segoe UI"` | `"Microsoft YaHei"` | 列表解析不到任何一款时 |
  |---|---|---|---|
  | `·` U+00B7 | 2.4498px | 2.7202px | **11.3000px（4.6×）** |
  | 空格 U+0020 | 3.0954px | 3.3436px | 2.5312px |

- **因此"要不要把 CJK 字体排到拉丁前面"的答案是：不要。** 对本产品，把 CJK 提前只会让 UI 里的拉丁文案（`CHINA · UNIVERSITY ATLAS`、数字、`＋/−`）改用 YaHei/PingFang 的拉丁字形（Windows 上明显更差）；而汉字无论如何都会落到 CJK 字体。拉丁在前是正解。
- **两处非标准别名可以保留**：`-apple-system` / `BlinkMacSystemFont` 只在 Apple 平台解析，在 Windows/Linux 上等于不存在的家族（实测：把整个候选栈用在 Windows 上，汉字度量与 YaHei-only 完全相同，说明这两个别名没有造成任何"被截走"）。它们是无害的 macOS 优化项。
- **`Arial` 放在末尾是对的**：Linux 上它通常由 `fonts-liberation` 以别名提供，作为拉丁兜底；`sans-serif` 最终兜底保留。

## 描边规则

### 先纠正一个前提：`paint-order:'stroke fill'` 下描边**永远不可能吃掉笔画**

标签 `<text>` 同时带 `stroke:'#ffffff'`（`MAP_STYLE.label.halo`）、`stroke-linejoin:'round'`、`paint-order:'stroke fill'`。`paint-order:stroke fill` 表示**先画描边、再把填充盖在上面**，于是描边只有轮廓外侧的那一半可见（`t = stroke-width/2`），字形本身一个像素都不会被覆盖。

实测（4× 超采样，白底，统计暗像素）：`浙江大学` @11.3px/700，无描边与 2.8px 描边的暗像素数 **3110 vs 3110**；`一` 单字 @11.3px/800 **294 vs 294**；@8px/700 **1475 vs 1460**（1% 差异来自轮廓抗锯齿）。**所以"halo 吞掉字形"不能按"描边盖住笔画"理解**，它真实发生的是另外两件事：

1. **描边吃掉的是字形的"负空间"**：汉字靠笔画之间的白色空隙（字怀）辨形。t=1.4px 的白色描边会在每一条笔画两侧各铺 1.4px 白，笔画间 1–2px 的空隙被白填满，字怀与 halo 连成一片白 → 字看起来不是"被覆盖"，而是**空心化、糊成一团白底墨点**，负空间信息丢失。
2. **描边吃掉的是底图**：每个字周围的白色面积 = 字形 ink + 周长×t；一屏 30+ 标签、每标签 4–7 字，白描边在浅色底图上铺出大片白斑，削弱"色块即行政区"的信息。

## 文本测量

### 现在的实现（live）

`src/app.js:66` `textWidth(s, fs, weight)`：把一行文字塞进 `#measureLayer` 里的隐藏 `<text>`（`'font-family':FONT_STACK`，`font-size` 保留一位小数），取 `getBBox().width`，按 `weight|size|s` 缓存（`widthCache`），失败才回落到 canvas `measureText`（`app.js:71`，同样用 `FONT_STACK`）。`#measureLayer` 的隐藏方式是 `visibility:hidden`（`styles.css:105`）—— 这是对的：实测 `visibility:hidden` 下 `getBBox()` 正常返回（46.203），而 `display:none` 下 `getBBox()` 在 Chrome 里仍返回 46.203、但 `getBoundingClientRect()` 返回 0×0（规范说应为空盒，**不要依赖 `display:none` 下的 getBBox**）。

### 一致性实测（Windows / Chrome 152，`浙江大学`，11.3px，w700）

| 来源 | 值 | 与 SVG 真实排版之差 |
|---|---|---|
| canvas `measureText`（旧实现） | 45.200 | −0.003px（−7e−5） |
| `getComputedTextLength()`（SVG advance） | 45.203 | 0 |
| `getBBox().width`（ink box，现实现） | 46.203 | +1.0px（字形两侧的边距，随字体不同而变化） |

**因此任务书里"Windows 上每个标签宽度都是错的"这一条不成立**，需要精确纠正：

1. **测量栈 vs 绘制栈在 Windows 上本就同族**（前提里的推理是对的）：标签属性以 `"PingFang SC"` 开头，但 PingFang 在 Windows 上不存在 → 逐字回退到第二款 `"Microsoft YaHei"`，正是测量用的那款。实测佐证：`'"PingFang SC","Microsoft YaHei",…'` 与 `'"Microsoft YaHei"'` 渲染同一串汉字的 `getBBox` 完全相同。**新的 `FONT_STACK` 也依然把汉字交给 YaHei**（实测候选栈 = YaHei-only 的 ink box）。所以 Windows 上"测量=绘制"是成立的事实，不是巧合。
2. **旧实现在 Windows 上的数值误差 ≈ 0.003px**，因为汉字 advance 恰好是 1em，且**字重不改变 advance**：实测 w=300/400/500/600/650/700/800/900 的 `getComputedTextLength('浙江大学')` 全部 = 45.203 = 4×11.3。这正是 `textWidth` 的 `weight` 参数对本产品几乎无意义的原因（对拉丁有影响，对汉字没有）。
3. **macOS 的旧问题是"真实但被高估"的**：旧测量栈 `"Microsoft YaHei","Noto Sans CJK SC",sans-serif` 在 macOS 上前两款都不存在，最终经 `sans-serif` 落到系统 CJK 字体（通常是 PingFang SC，与绘制栈相同）；而 PingFang SC 与 YaHei 的汉字 advance **同为 1em** → 纯汉字串的**宽度**误差同样接近 0（未实测，推理）。**不该再对外说"macOS 上每个宽度都是错的"**；能确定的是"没有任何机制保证它是对的"，以及 ink box 的边距不同（实测 YaHei 的 ink 比 advance 宽 1.0px，而"解析不到家族"的兜底 ink 与 advance 等宽）—— 量级 1px，被 `+9` 的盒宽余量和 3px 碰撞容差吸收。
4. **真正会炸的不是汉字，是混排字符。** 家族选择只对"多款字体都能画的字符"生效，而这类字符的宽度差可以到 4.6 倍（实测 `·`：Segoe UI 2.45 / YaHei 2.72 / 解析不到 11.30）。当前 14 条路线渲染出的标签文本**只含汉字**（实测：`v5.8-visual-audit.json` 的 `labelTexts` 里除连接用的空格之外没有任何 ASCII 字符，`·` 只出现在 UI 文案与导出 SVG 页脚），但 `city-layer.js:116` 的 `textTokens()` 明确把 `' '`、`'　'`、`'·'`、`'-'`、`'/'` 当作独立 token 处理 —— 也就是说"标签里出现 `·` 或 `-`"是代码预期内的一次数据更新之遥。**这才是"测量字体必须等于绘制字体"的真正理由**，而现在的实现（标尺与标签都用 `FONT_STACK`）已经把它堵死了。

### 该用哪个 API（带 `paint-order` 的 SVG 文本）

- **主路径用"同一套属性的隐藏标尺 + `getBBox()`"或 `getComputedTextLength()`**，两者都排除描边，这正是布局想要的（描边是白色装饰，不该进碰撞盒；现在的 `+9` 盒宽余量足够吸收 `sw/2≈0.6px`）。
- **一次重要纠正**：任务书（以及 `tests/visual-layout.mjs` 的注释 `stroke and paint-order are included`、`v5.8-visual-audit.json` 的 `generatedAtNote`）认为 `getBoundingClientRect()` 含描边。**在 Chrome 152 上实测不成立**：`<text>` 带 `stroke-width:10` 时 `getBoundingClientRect().width = 21`（与不带描边时相同），`<rect>` 带 `stroke-width:10` 时 `getBoundingClientRect` 仍是 100×20。**两个 API 都排除描边。** 后果：现有审计的 overlap / clipped 几何是 **ink box**，两个标签各带 1.4px 白描边相互侵入时审计看不到（白压白无害，但"描边不会压到邻字"这件事目前**没有任何断言覆盖**）。做法二选一：接受（白描边重叠无害），或在盒宽里显式加 `sw`。
- **每帧布局的代价**：标尺路径每次未命中缓存都要 `append + getBBox()（同步文本布局）+ remove`。缓存键是 `weight|round(fs,1)|string`，平移/缩放不改字号时全部命中，代价可接受。两个注意点：(a) 缓存把 fs 四舍五入到 0.1，而绘制用的是 `toFixed(2)`，最多 0.05px 差 —— 无害；但**如果将来给标签加 `letter-spacing`，键里必须带上它**，因为字距会改宽度（实测 4 字加 0.4px 字距：`getComputedTextLength` 45.203→46.813，ink box 46.203→47.813；`text-anchor:middle` 下中心不偏移，实测 499.5 不变）。(b) **兜底逻辑有个静默失败点**：`app.js:70` 的 `if(!w&&w!==0)` 在 `getBBox()` 返回 **0** 时不会走 canvas 兜底（`!0===true` 但 `0!==0` 为假），宽度会变成 `0+9=9px`，所有标签盒塌缩、碰撞检测失效。建议改成 `if(!(w>0))`，并在验收里断言 `w>0`。

### 现状评价

现在的实现方向是对的（浏览器自测，天然与绘制同栈），比"canvas 估算"强；canvas 兜底保留即可，但要知道它有两个固有短板：**无法表达 `letter-spacing`**，且**独立解析字体族**（正是当初产生分歧的那条路径）。对本产品（纯汉字标签）它在 Windows 上与真实 advance 差 0.003px，可以当作等价兜底。

| 提示 | 现状 | 建议 | 依据 |
|---|---|---|---|
| `-webkit-font-smoothing:antialiased` | **已写在 `styles.css:57` 的 `body` 上** | **删掉**（或至少确认它不影响 SVG 标签） | 只在 macOS 生效，且它是**关闭次像素抗锯齿** → macOS 上 6.4–12px 的 CJK 会明显变细、发虚。本产品标签最小 6.4px、正文 10–14px，正落在这个不该关的区间。Windows/Linux 上是空操作。这是本次唯一一条负收益提示 |

| `font-kerning` | 无声明 | **保持不设**（默认 `auto`） | 汉字无 kern 对；标签实测纯汉字。只在拉丁 UI 文案上有微小意义，`auto` 已足够 |

| `-webkit-font-smoothing` / 字重 800 | `app.js:89` 导出标题 `font-weight:800` | 改成 `700` | 见下 |

**`font-weight:800` 会不会在 Linux CI 上伪粗？** 结论：**不会，但 800 本身没有意义**。

- Windows 实测：YaHei 有 Light/Regular/Bold 三款真实字面，`300→Light`、`400/500→Regular`、`600…900→Bold`；**700 与 800 的 ink box 逐位相同**（w=46.203, h=15），没有合成加粗，也没有变粗。
- Linux CI（Noto Sans CJK SC）：`fonts-noto-cjk` 只提供 Regular + Bold 两个字面文件（Black 在 `fonts-noto-cjk-extra`）→ `800` 同样落回 Bold，**不会伪粗**（未实测，需 CI 上确认；若镜像里只有 Regular 一款 CJK 字体，任何 ≥600 的请求才会触发合成加粗）。
- macOS（PingFang SC）：没有 Bold，只有 Semibold → `700/800` 都落 Semibold。
- **真正的风险是"只有一个字面的环境"**（某些精简容器里的 WenQuanYi Zen Hei 等）：合成加粗靠轮廓外扩实现，会把笔画外侧再加粗 ~0.02–0.03em，**与过粗的白色描边叠加**，在小字号上直接把字怀糊死。防它的正确做法不是 `font-synthesis:none`（那会丢掉"校名比地名重"的层级），而是**只用各平台真实存在的字重档**——`LABEL_TYPO` 的 `500 / 700` 已经做到了；`app.js:89` 的 `800` 属于遗留，改成 `700` 即可（Windows/Linux 渲染结果逐像素相同，macOS 从 Semibold 变 Semibold，等于零风险）。

## 验收方式

1. **平台字体存在性（CI 必做，且必须用 fontconfig，不能用几何）**
   - `fc-list :lang=zh` 非空；`fc-match "Noto Sans CJK SC"` 返回 Noto 而不是 DejaVu/Liberation。
   - 若为空 → 该 CI 上所有标签是 tofu，而现有全部几何断言仍会通过（advance 恒为 1em）。这是"必须外部断言"的理由。
   - **禁止**用 `document.fonts.check()` 做这个判断（实测对不存在的家族也返回 `true`）。
2. **测量↔绘制一致性断言（唯一能捕获"测量字体≠绘制字体"的检查）**
   - 每条路线渲染完成后，对 `#labelLayer` 的每个 `<text>`：取 `el.getComputedTextLength()`，与 `textWidth(el.textContent, Number(el.getAttribute('font-size')), Number(el.getAttribute('font-weight')))` 比较，断言差值 ≤ 0.5px（今天应 ≤ 0.05px）。
   - 顺带断言每个值 `> 0`（防 `getBBox()` 返回 0 时盒宽塌缩成 9px 的静默失败，见 `## 文本测量`）。
3. **描边断言（替换现有 `heavyHalo`，它现在是假绿灯）**
   - 现有口径 `tests/visual-layout.mjs`：`heavyHaloLabels = stroke >= fs`。要触发需 `fs ≤ 2.8`，而字号下限是 6.4/8 → **结构上永远为 0**。14 条路线的 `heavyHaloLabels: 0` 因此不构成任何保证；按 `sw/fs` 口径，现状 0.16–0.25 属于偏粗区间。
   - 改为：`warn` 当 `sw > 0.14·fs`；`fail` 当 `sw > 0.20·fs` 或 `sw < 1.0`；并把 `stroke/fs` 的最大值写进 `summary`（而不是只报计数）。
   - 加一条组内一致性断言：同一 `<g data-label-id>` 内所有 `<text>` 的 `stroke-width` 必须 ≤ 该组最小 `font-size` 的 0.14 倍（防止"按粗字定描边、套到细字行上"）。
4. **导出 SVG 自检**：`makeSVG()` 产物字符串里断言 (a) 根节点带 `font-family`，(b) 不出现 `'"Microsoft YaHei",sans-serif'` 这类单平台字面量，(c) 标签文本节点的 `font-family` 与 `FONT_STACK` 逐字相等。
5. **字形指纹（记录用，不要做成硬断言）**：在页面里测 `'浙'` 的 `getBBox().height`——实测 Windows/YaHei = 15，而 PingFang-缺失兜底 = 16。它能在"某平台悄悄换了字体"时给出信号；但 macOS/Linux 本来就该不同，所以只记录进 `reports/visual/*.json`，阈值报警交给人看。
6. **视觉回归**：保留现有 14 张截图。要注意字体回退与描边比例问题**都不会改变几何**（advance 恒 1em、ink box 变化 ≤1px），所以几何审计通过 ≠ 字体正确；描边比例与字体族这两类问题只能靠上面的 2/3/4 与人工看图。
